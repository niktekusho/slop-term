# 18 — SFTP transfers

**What to build:** The user uploads and downloads files and folders from the SFTP pane, including by dragging files in from the OS, without making the terminal lag. Transfers queue per Tab with progress, cancel and retry, and an existing target asks overwrite, skip or keep both.

**Spec:** [Spec: slop-term v1](../../slop-term-v1/spec.md)

**Blocked by:** 08 — Password login and keychain provider; 17 — SFTP pane browsing and file actions

**Status:** done

- [x] Transfers run on a second connection opened on the first transfer and closed after 5 minutes with no transfers. It logs in with the session's key, agent or Credential reference, or the password typed for the Tab, and must present the host key the Tab accepted: a different key blocks with the changed-key warning in the pane, never a question.
- [x] Hosts that asked a keyboard-interactive prompt run transfers on the Tab's connection instead.
- [x] Keepalives on the transfer connection use the Tab's values.
- [x] One queue per Tab, one file at a time; folders transfer with everything inside.
- [x] Download saves to the last folder used (Downloads the first time); Download to… opens a folder picker; Upload files… opens a file picker; files dragged in from the OS upload, with a dashed overlay "Drop to upload to <path>". No drag out.
- [x] Transfer list docked at the bottom under "Transfers" with the active count; a row shows direction, name, target folder, progress bar with percent, bytes and speed, and cancel. Finished items clear after a few seconds; a finished download shows "Saved to <folder>" as a link that reveals the file in Explorer or Finder. Failed rows show the reason in red and retry.
- [x] The collapsed strip shows the running upload's percentage.
- [x] Conflict dialog names the file, compares size and modified time on this computer and on the host, and offers Overwrite, Skip and Keep both (` (1)` suffix), with "Apply to the other N conflicts".
- [x] Closing a Tab with pending transfers asks first and offers "Show local copy".
- [x] On a drop running transfers fail and stay retryable.
- [x] Back-end tests against the Docker server: upload, download, recursive folder, conflict choices, second connection idle close, pinned host key mismatch, keyboard-interactive fallback to the Tab's connection.

## Test coverage

Back end: `src/backend/transfers.test.ts`. Its Docker block runs against OpenSSH. Its in-process block uses `startFakeSshServer` with `sftp: true` for what the Docker image can't stage: connection counts, a host key change, keyboard-interactive questions, keepalives per connection and held writes. The spec's Testing Decisions name the fake for that. UI: the "transfers" block of `src/renderer/SftpPane.test.tsx`, against `FakeBackend`.

- Second connection: in-process "opens the transfer connection on the first transfer and closes it when idle" counts connections: 2 during the upload, 1 after the idle time, and a third for the next upload. `SLOP_TRANSFER_IDLE_MS` shortens the 5 minutes. "logs the transfer connection in with the password typed for the Tab, without asking" sees one secret question and two connections. Every Docker test logs in with a key. A Credential reference goes through the same `known()` read as a typed secret, but no test reads one on the transfer connection.
- Accepted host key: in-process "blocks with the changed-key warning…" changes the fake's ed25519 key. The row fails, a `transferKey` event carries both fingerprints, and no `hostKey` question goes out. "fails with a reason when the host no longer offers the type of key the Tab accepted" covers a host that switched to RSA. The handshake fails before any key reaches the check, so the row names the reason and the pane shows no fingerprints. UI "warns in the pane when the transfer connection meets a key other than the Tab's" checks the warning and that it offers no Trust or Replace button.
- Keyboard-interactive: in-process "transfers on the Tab connection for a host that asked keyboard-interactive questions" sees one connection and one question.
- Keepalives: in-process "sends keepalives on the transfer connection at the Tab's interval" counts at least 2 keepalives on each of two connections with `ServerAliveInterval 1`. The default 15 s sends none in that time. The test failed with the transfer connection's interval fixed at 15 s.
- Queue and folders: Docker "uploads a file…", "downloads to Downloads…" and "transfers folders with everything inside, both ways", which includes an empty subfolder. In-process "cancels a running transfer and a queued one" holds the fake's writes, so the second item stays queued while the first runs. A link inside a folder is skipped (`ponytail:` in `transfers.ts`), and no test covers it.
- Download, Download to…, Upload files… and drag in: Docker "downloads to Downloads the first time, then to the last folder a Download to… picked" checks `downloadFolder` in the settings. UI "downloads the selected rows…", "uploads picked files…" and "uploads files dragged in from the OS, with a dashed overlay…". The dashed border is CSS, which jsdom doesn't apply. `webUtils.getPathForFile`, the pickers and `shell.showItemInFolder` run in the preload and the main process, which no test starts. No drag out: the pane sets no `draggable`, so there is nothing to test.
- Transfer list: UI "lists transfers with the active count, direction, folder, progress, bytes and speed, and cancels", "shows a finished download as a Saved to link that reveals the file, and clears it after a few seconds" (3 s) and "shows the reason of a failed transfer in red and retries it". The red comes from `.transfer-error`.
- Collapsed strip: UI "shows the running upload's percentage on the collapsed strip".
- Conflicts: Docker "asks about each existing target with both sides, and overwrites, skips or keeps both" checks sizes, modified time, `others`, and `three (2)` when `three (1)` is taken. Docker "gives one answer to the other conflicts of the batch, keeping both of each" checks `report (1).txt`. UI "asks about a conflict with both sides, and answers for the other conflicts too". The queue waits on the answer, so UI "opens a collapsed pane to ask about a conflict, and opens it again on a switch back to a Tab still asking".
- Closing a Tab: UI "asks before closing a Tab with pending transfers, and offers Show local copy" and "closes a Tab whose transfers are all finished or failed without asking". For a pending download the button shows its folder, because the file may not exist yet. No test covers that branch. The dialog reads the pending list live, so its count stays right while transfers finish, and it captures nothing when it opens.
- Drop: in-process "fails a running transfer on a drop and retries it after the reconnect". In-process "asks again on a retry of a transfer whose conflict question a drop voided" failed before each item recorded whether its conflict check ran.
- Platform facts checked by running them: about 1 in 150 ed25519 keys from `ssh2.utils.generateKeyPairSync` fail `ssh2.utils.parseKey`. A loop under Electron's Node (`ELECTRON_RUN_AS_NODE=1 electron keys.mjs`) found 13 of 2000. The fake server retries until a key parses. Not checked by running: Electron's docs say a Windows open dialog can't pick files and folders at once, so Upload files… picks files only, and folders upload by drag.
- Full suite: two full runs on this machine took 351 s, not the 72 to 79 s that retro 13 measured. They failed 6 and then 4 tests, all on fixed timeouts, in the folders, KeePass, `ssh-tab` and two UI files. Run alone, `ssh-tab`, `transfers` and `sftp` passed (56 tests), folders, `ssh-tab` and KeePass passed (65), and the two UI files passed (83) on the second try. The first run also showed one real break: the fake server's new SFTP made "fails a Test at SFTP on a server without the SFTP subsystem" fail. SFTP on the fake server is now opt-in.
